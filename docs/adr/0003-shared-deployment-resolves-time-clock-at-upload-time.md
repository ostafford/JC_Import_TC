# One shared deployment routes Import Runs by upload, never by live chat Q&A

A client can have several Connecteam Time Clocks (one per physical location), each feeding its own Xero connection, while still sharing one Connecteam Chat conversation and one set of Admins. Two architectures were genuinely available: deploy N independent Relay/Importer/Chat Link stacks (today's existing single-Time-Clock model, one per location, zero new engineering), or extend a single shared deployment to route each Import Run to the right Time Clock. We chose the latter — N separate chats for what an Admin experiences as one workflow ("upload the roster") is exactly the friction and error surface this feature exists to remove.

Within the shared-deployment shape, routing could also have been resolved via a live chat round-trip (Importer posts "which Time Clock?", an Admin replies, the reply is parsed) — the idea the client-facing side of this project first proposed, since a webhook is already listening on the conversation. We rejected it: Connecteam's Chat API has no message threading (every message, including the Importer's own, is a flat top-level message — [issue 05](../../.scratch/connecteam-schedule-import/issues/05-chat-confirmation.md)/[06](../../.scratch/connecteam-schedule-import/issues/06-chat-link-setup-flow.md)), so there is no reliable way to attribute a later, un-threaded reply to a specific pending question, especially with several Admins active in the same conversation or a second upload arriving before the first is answered. Instead, resolution happens entirely from the upload itself (a signal in its content, caption, or filename — mechanism tracked in the [Multi-Time-Clock Routing map](../../.scratch/multi-time-clock-routing/map.md)), with no server-side conversation state to get out of sync.

This is hard to reverse once Admins are trained around one interaction model, and not the obvious choice given a live webhook is sitting right there — worth recording so a future reader doesn't "fix" this back into a chat round-trip without re-discovering the threading problem first.
