# Queue consumers never auto-retry an Import Run

The Importer's queue consumer processes one Import Run per message and writes real Time Activities to a live Connecteam account. Its "already written" state comes only from the Schedule Export file's own Check-In/Complete columns, never from a live check against what the Importer has already written that run — so a retry after a partial failure has no way to skip rows that already succeeded. On 2026-09-25, a real Import Run crashed partway through (Workers Free plan's subrequest cap) with `max_retries: 3` still configured, and Cloudflare Queues silently re-ran the entire pipeline three times in under two minutes, duplicating real Time Activities for 23 employee/date combinations with no Chat notification at all ([issue 18](../../.scratch/connecteam-schedule-import/issues/18-queue-retry-duplicated-writes.md)).

We decided `max_retries: 0` on every queue consumer that performs the actual writes, permanently — not a temporary mitigation pending a better fix. A failed Import Run stops and posts a crash notice to Chat naming that some shifts may already be written and that nothing will retry automatically, so the Admin knows to check for duplicates before re-uploading. This trades away automatic recovery from transient failures (a crash now always requires the Admin to re-trigger manually) for the guarantee that a failure never silently duplicates payroll data.

This is now standing policy for any write-heavy piece built under this directory (see the repo's `CLAUDE.md`), not just this one queue: real per-row duplicate protection (checking live against Connecteam before every write, not just the export file's own columns) would make retries safe again, but is a larger design change than was warranted for incident response and remains a known, not-yet-done follow-up.
