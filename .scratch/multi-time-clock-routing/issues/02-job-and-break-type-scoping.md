## Question

The original map's issue 08 documented Break Type selection (`GET .../manual-breaks`) as account-wide, and issue 12 documented Job matching as scoped per Time Clock via `instanceIds` — but issue 08's "account-wide" conclusion was only ever verified against a single-Time-Clock test account. Confirm, via developer.connecteam.com's docs (and a live multi-Time-Clock account if docs are ambiguous):

- Is `GET .../manual-breaks` actually account-wide, or scoped per Time Clock (e.g. via an `instanceIds`-style param, mirroring Jobs)? If it's per-Time-Clock, the existing "pick one default Break Type per paid/unpaid category at setup, once" design (issue 08) breaks and needs to become per-selected-Time-Clock, same as Job matching already is.
- Confirm the exact shape of a Job's Time-Clock association (`instanceIds` — is it always an array, can it be empty/all-Time-Clocks, etc.) so the Importer's existing Job-matching call can be pointed at whichever Time Clock a given Import Run resolves to, instead of a single static config value.

## Answer

Full research trail (primary-source citations against developer.connecteam.com and help.connecteam.com): `.scratch/multi-time-clock-routing/research/job-and-break-type-scoping.md` on branch `research/job-and-break-type-scoping`.

**Break Types are not simply "account-wide" — issue 08's premise needs correcting for multi-Time-Clock accounts.** The canonical break rule (its `id`, name, paid/unpaid flag, duration) is defined once at the company level, not duplicated per Time Clock — confirmed via Connecteam's Help Center ("How to Set Up Breaks (Paid & Unpaid)"): "Break rules belong to the company, not to a single Time Clock... you set a break up once instead of repeating it per clock." But that same article immediately adds: "If you need a rule to apply to certain clocks only, you can limit that rule to specific Time Clocks." So the *effective, usable* set of Break Types can legitimately differ from one Time Clock to another, even though the underlying definitions are shared. This is also why the API never offers an account-level "all breaks" endpoint — `GET /time-clock/v1/time-clocks/{timeClockId}/manual-breaks` is the only way to read them, always scoped by `timeClockId` ("Get multiple manual breaks of a time clock"). The enablement flag is per-Time-Clock too: the write-path error is phrased "manual breaks are disabled **for the given time clock**" (not "for this account"), and Connecteam's own Time Clock General Settings article confirms the general pattern — "General settings apply to the entire Time Clock" — with only the payroll export display format called out as the one account-wide exception.

**Consequence for this project's design**: issue 08's "pick one default Break Type per paid/unpaid category, once, at setup" breaks the moment a second Time Clock is involved — the Admin's chosen default might not exist on, or might be disabled for, a Time Clock a given Import Run later resolves to. This must become **per-selected-Time-Clock**: call `GET .../manual-breaks` (and read `areManualBreaksEnabled`) against the specific `timeClockId` an Import Run resolves to, and have the Admin pick (or re-pick) a default per Time Clock — the same shape Job matching (issue 12) already uses, not a new pattern to invent.

**Job `instanceIds` shape, confirmed against the Jobs guide pages and OpenAPI schema**: always an array, never a bare scalar, in all three places it appears — the required `instanceIds` field on Create Jobs ("List of scheduler or time clock IDs"), the optional `instanceIds` filter on Get Jobs ("Filter by scheduler or time clock IDs", OpenAPI-typed `array | null`), and every Job object's own wire shape (`"instanceIds": [6833518]`). No "all Time Clocks" sentinel value is documented anywhere. Whether an empty array is accepted is genuinely undocumented — not confirmed either way, stated plainly rather than guessed. A Job can span more than one instance at once (multi-element arrays are validated per-element, per the documented "Invalid instance ids" error), confirming issue 12's "scoped to one or more instances" framing. Practical effect: the existing Job-matching call (`GET /jobs/v1/jobs?jobNames=...&instanceIds=<timeClockId>`) needs no shape change — it already takes exactly this kind of ID — only the value fed into it needs to become the Import Run's resolved Time Clock instead of a static config value.
