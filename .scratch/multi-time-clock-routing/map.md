# Multi-Time-Clock Routing — Map

## Destination

A vetted technical spec (not code yet) for routing a **single shared** Relay/Importer/Chat Link deployment across **several** Connecteam Time Clocks — one per client location — so that an Admin's file upload alone, with **no live chat back-and-forth**, determines which Time Clock's Time Activities, Jobs, and Break Types an Import Run resolves against. Built as a first-class, general capability of the project (documented for any adopter with multiple Time Clocks), not a one-off for a single client.

## Notes

- Vocabulary is canonical in [CONTEXT.md](../../CONTEXT.md) — **Time Clock Signal** (the raw value an upload carries — caption, filename, or in-file field, exact source still open) and **Time Clock Mapping** (the Importer's own config resolving a Signal to a Time Clock) were just added for this map. Use them, not synonyms like Location/Site/Branch — Connecteam has no such entity of its own.
- Builds on the resolved [Connecteam Schedule → Timesheet Import map](../connecteam-schedule-import/map.md) — treat its Decisions-so-far as settled background, especially:
  - [issue 04](../connecteam-schedule-import/issues/04-import-failure-policy.md): partial-success-by-default, skip-and-flag-to-Chat policy for any per-row failure — a Job/Time-Clock mismatch should fail the same way an unmatched Employee does.
  - [issues 05](../connecteam-schedule-import/issues/05-chat-confirmation.md)/[06](../connecteam-schedule-import/issues/06-chat-link-setup-flow.md): Connecteam's Chat API has **no message threading** — every message, including the Importer's own, is a flat top-level message. This is *why* upload-time resolution was chosen over a live "which Time Clock?" chat round-trip: there's no reliable way to attribute an un-threaded reply to a specific pending question, especially with several Admins active in one chat.
  - [issue 08](../connecteam-schedule-import/issues/08-break-type-selection.md): Break Type selection was verified only against a single-Time-Clock account — its "account-wide" scoping is *not yet confirmed* for a multi-Time-Clock account (see issue 02 of this map).
  - [issue 12](../connecteam-schedule-import/issues/12-job-tracking-required.md): Job matching already takes an `instanceIds` param — a Job can be associated with more than one Time Clock.
  - [issue 16](../connecteam-schedule-import/issues/16-time-clock-id-not-discoverable.md): `listTimeClocks()` already exists and is reused here.
  - [ADR 0001](../../docs/adr/0001-relay-never-touches-customer-data.md): Relay never touches business data — Time Clock Mapping lives in the Importer's own config, never the Relay. Settled, not open for re-litigation here.
- [ADR 0003](../../docs/adr/0003-shared-deployment-resolves-time-clock-at-upload-time.md) records why this map exists at all: one shared deployment (not N independent stacks), routing resolved from the upload itself (not a live chat Q&A round-trip). Settled, not open for re-litigation here — the "rejected alternative" reasoning lives there in full.
- Default mode is planning: tickets resolve decisions, not deliverables. No code until the user explicitly says this map should carry execution.
- Reference: Connecteam developer docs (developer.connecteam.com), specifically `/docs/chat-webhook` (the `content` field, confirmed to sit alongside `attachments` in a `message_created` event), `/jobs/v1/jobs` (`instanceIds`), `/time-clock/v1/time-clocks`.
- When resolving a ticket, call the grilling and domain-modeling skills unless the ticket type says otherwise.

## Decisions so far

- [Job and Break Type scoping](issues/02-job-and-break-type-scoping.md): confirmed against developer.connecteam.com and help.connecteam.com — Break Types are defined once at the company level, not duplicated per Time Clock, but a rule can be restricted to specific Time Clocks and the enablement flag (`areManualBreaksEnabled`) is itself per-Time-Clock, so issue 08's "pick one default Break Type per category, once, at setup" doesn't hold for a multi-Time-Clock account; it must become per-selected-Time-Clock, same shape as Job matching. Job `instanceIds` is confirmed array-shaped everywhere it appears (create, filter, and wire response), with no documented "all Time Clocks" sentinel and no confirmed empty-array support — the existing Job-matching call needs no shape change, only a dynamic `timeClockId` per Import Run instead of a static config value.
- [Time Clock Signal source](issues/01-time-clock-signal-source.md): no in-file, Employee-based, or Time-Clock-based signal exists (Schedule Export schema, Users API, and TimeClock API all checked and ruled out). **Confirmed live** (created and cleaned up two real throwaway Jobs against the demo account's real Time Clocks): a Job's `instanceIds`, queried by name with no `instanceIds` filter, reveals which Time Clock a Job belongs to — reusing the Importer's existing Job-matching step (issue 12) as the primary Time Clock Signal, live-derived every run with nothing to go stale as the client's Jobs/Time Clocks change. Only works when every Job resolved from one Schedule Export agrees on a single Time Clock, which requires the client's own Jobs to be set up Time-Clock-exclusive — a real client-configuration dependency, not guaranteed. Fallback tracked in [issue 05](issues/05-fallback-signal-when-job-resolution-is-ambiguous.md).
- [Fallback signal when Job resolution is ambiguous](issues/05-fallback-signal-when-job-resolution-is-ambiguous.md): build a fallback rather than failing outright. When Job `instanceIds` resolution doesn't yield exactly one Time Clock, fall back to matching the upload's caption text (`data.message.content`) against a Time Clock's real name via `listTimeClocks()` — deliberately not a keyword+mapping, to keep both signals live-derived with nothing configured to go stale. **Live addendum**: caption-in-compose-UI confirmed working; also corrected a real gap found live — a caption was silently ignored whenever Jobs resolved cleanly, so a disagreeing caption is now a surfaced **conflict** (aborts, names both interpretations in Chat) rather than a silent override.
- [Ambiguous resolution failure policy](issues/03-ambiguous-resolution-failure-policy.md): when both resolution stages fail to produce exactly one Time Clock, abort the whole Import Run before any row is processed (structurally forced — no write call can be made without a resolved `timeClockId`) and post a brief, non-technical Chat notification listing this Importer's configured Time Clock names, so the Admin knows exactly what caption to use on re-upload. Safe to just ask for a re-upload since nothing was written yet — not a retry of ADR 0002's concern.
- [Concurrent runs & confirmation clarity](issues/04-concurrent-runs-confirmation-clarity.md): confirmed by reading the actual code (not just architecture) that `timeClockId` already flows as an explicit per-invocation parameter (`config.timeClockId` / `env.TIME_CLOCK_ID`), never a shared global — concurrent Import Runs for different locations can't cross-contaminate. Chat confirmations name the targeted Time Clock only once 2+ Time Clocks are configured; single-Time-Clock deployments (the common case) keep today's simpler message unchanged.
- [Setup UX for multiple Time Clocks](issues/06-setup-ux-for-multiple-time-clocks.md): validated live via a runnable prototype (branch `prototype/setup-ux-multi-timeclock`) — multi-select Time Clock picker, a per-selected-Time-Clock Break Type sub-step (skipping any with breaks disabled), and an add-one-more-vs-reconfigure-everything re-entry point on re-run all confirmed to feel right. Also surfaced live: plain-text terminal output felt flat, fixed with plain-ANSI colour/spacing (no new dependency) — carries into the real implementation whenever this map moves to execution.
