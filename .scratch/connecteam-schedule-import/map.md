# Connecteam Schedule → Timesheet Import — Map

## Destination

A vetted technical spec (not code yet) for a personal, open-source, self-hosted **Connecteam Schedule → Timesheet Import** tool: an Admin exports their Connecteam Schedule and uploads it as a file attachment in a linked Connecteam Chat conversation; the Relay (a lightweight hosted website, storing only a Chat Link per Admin) forwards a "go" trigger to the Admin's own Importer; the Importer — holding the Admin's own Connecteam API token — downloads the file, parses it, matches rows to Employees, and writes shift (and break, if derivable) Time Activities, only where no real clock-in entry already exists. On-demand trigger only; continuous auto-sync is a future phase, out of scope here.

## Decisions so far

- [Scheduler break support](issues/02-scheduler-break-support.md): Connecteam's Scheduler shift object supports breaks natively via the API — but corrected by real export samples in issue 01: the Schedule Export itself *does* carry break data too, as an aggregate `HH:MM` duration per paid/unpaid category (not a full per-break breakdown).
- [Real Schedule Export sample](issues/01-real-schedule-export-sample.md): confirmed exact export schema (23 columns), Employee identity is a plain full-name string with no ID/email, no stable per-row ID exists, and Check-In/Complete columns may let the Importer detect an already-worked shift without a separate API call.
- [Employee identity matching](issues/03-employee-identity-matching.md): batch-resolve export names via `GET /users/v1/users?fullNames=...&userStatus=all`, then case-insensitively confirm `firstName + " " + lastName` client-side; skip and flag the row for the Admin on zero matches, an archived-only match, or more than one match — never auto-pick. **Corrected live**: `fullNames` must be repeated query params, not comma-joined — the comma-joined guess silently matched zero Employees for any multi-name batch (fixed; verified 10/10 real Employees matching). Case-insensitivity confirmed live too (issue 11).
- [Import failure policy](issues/04-import-failure-policy.md): partial-success-by-default for every per-row failure type (unmatched Employee, locked day, already-has-real-entry, other write errors) — skip and flag, never abort the whole run, except on a systemic auth/authorization error. Locked-day flags must name the Employee and must reach Chat. Import Run outcome record defined: counts + per-row `{date, employee name, outcome, reason}`. Side effect: the GET-before-POST check this ticket requires (Connecteam has no server-side duplicate protection) also makes re-processing the same Schedule Export harmless — a row whose shift already has any entry, imported or real, gets skipped.
- [Chat confirmation](issues/05-chat-confirmation.md): the Importer always posts a result message — brief one-liner on full success, and on any failure a short text summary plus a separate attached report file (message text is capped around 500 characters in practice; full per-row detail goes in the attachment, not the text). No message threading exists in Connecteam's Chat API — every result is a new top-level message.
- [Chat Link setup flow](issues/06-chat-link-setup-flow.md): Relay login is magic-link email (no passwords); who can trigger an Import is governed entirely by Connecteam's own chat membership (an "Admin Only" group chat), not by the tool itself — correctly supports multiple Admins per company. Finding a conversation ID and creating its scoped webhook (`entityId`) both require a token the Relay never holds, so a one-time `importer setup` step does this using the Admin's own token, producing the values the Admin pastes into the Relay's form. One Chat Link per account, not per Admin. **Corrected live, built and verified end-to-end against a real account**: real webhook endpoint is `POST /settings/v1/webhooks` (not the originally guessed path) with an undocumented required `webhookVersion: 0` for chat; a `secretKey` given at creation is echoed back as `x-webhook-secret` on every delivery, so the Chat Link form gained a 4th field to verify Connecteam→Relay calls; the trigger payload carries `attachmentUrl`, not `fileId` (no fileId exists on the wire); chat-confirmation `senderId` must be a Custom Publisher ID, not an Admin's own userId; the webhook also fires for the Importer's own outgoing confirmation messages, requiring a `senderType === "user"` filter to avoid a self-triggering loop.
- [Break Type selection](issues/08-break-type-selection.md): the `importer setup` step always has the Admin pick a default Break Type per paid/unpaid category from a real picker (`GET .../manual-breaks`, returns `id`/`name`/`isPaid`/`duration`), uniformly regardless of how many types the account has configured. Accounts with manual breaks disabled (`areManualBreaksEnabled: false`) skip break-writing entirely. **Corrected live**: the write API needs a break's own real `start`/`end` (`{timestamp, timezone}`), not a bare duration — since the export still never gives a break a real start time (issue 01), the Importer derives one by centering the break(s) within the shift; total worked/break time still comes out exactly right, only the placement is invented. `isSplitShiftOnManualBreak` is a top-level request field, and splitting is by time overlap, not a `shiftTimeActivityId` reference. Verified end-to-end against a real account: 45 rows → 90 correctly-split shift segments + 45 correctly-placed breaks.
- [Job tracking required](issues/12-job-tracking-required.md): not anticipated by any prior ticket — some Time Clocks enforce job tracking and reject a shift write without a `jobId`. The Schedule Export's `Resource` column is the Job's title; resolved via `GET /jobs/v1/jobs?jobNames=...&instanceIds=...` (same repeated-param requirement as issue 03's `fullNames`), same skip-and-flag-on-no-match policy as Employee matching. Verified live: 5 distinct Resource values, all resolved correctly.
- [ToS sanity check](issues/07-tos-sanity-check.md): the Relay is self-hosted per deployer too (not one shared service run by this project's author — ADR 0001 updated), so every deployment stays entirely within one company's own account. Confirmed approved via an internal Connecteam conversation, no conditions attached.
- [Publishing & distribution](issues/09-publishing-distribution.md): MIT license (copyleft's rationale doesn't apply here — no shared-service scenario to guard against); README carries an "unofficial, not affiliated with Connecteam" disclaimer and documents the full setup order (token → `importer setup` → Relay login → paste values); no active promotion plan for now, published passively.
- [Multi-tenant hosted operation model](issues/13-multi-tenant-hosted-operation-model.md): a centrally-hosted mode where the project's author holds real clients' own Connecteam API keys is excluded permanently — confirmed against Connecteam's actual API ToS (Section 14: no processing another party's data, no redistributing the API; no partner/OAuth tier exists as an alternative path), not just by preference, so it doesn't get revisited by better engineering later (see [ADR 0001](../../docs/adr/0001-relay-never-touches-customer-data.md)'s addendum). ADR 0001's self-hosted-per-adopter model stays unchanged; what's added is a second supported self-hosted deployment target — Cloudflare Workers, deployed to the adopter's own account — alongside the existing local node+tunnel method, so a client can be shown both and choose based on their own cost/technical-comfort tradeoff. Separately, the project's author may run a demo instance under their own Connecteam test account to demo both options to prospective clients — never a real client's key. Feeds [issue 10](issues/10-tech-stack-and-hosting.md), which still has its own unresolved hosting-mechanics question.
- [Cloudflare deployment mechanics](issues/14-cloudflare-deployment-mechanics.md): the Relay/Importer split carries over to Cloudflare and becomes **mixable** (Relay on Cloudflare + Importer local is a supported third shape, alongside both-local and both-Cloudflare). Relay's Cloudflare version ships first — Worker + Durable Object (SQLite-backed, free-tier viable, chosen over KV for immediate consistency) — since it's simple and unconditionally solves issue 10's stable-URL problem. The Importer's Cloudflare version is deferred: real measured usage (issue 08's 45 rows → 135 write calls) already exceeds the Workers Free plan's 50-subrequest-per-invocation cap, so it will require the $5/month Paid plan, not Free — meaning "Cloudflare" is free only for the Relay/mixed shape, not the full-Cloudflare shape, and that distinction should be shown to clients honestly rather than assumed away. Onboarding leads with Cloudflare's real "Deploy to Cloudflare" button, `wrangler` CLI kept as documented fallback. The setup wizard stays local-only for now — no Cloudflare-aware wizard mode yet.
- [Importer's Cloudflare build](issues/15-importer-cloudflare-build.md): built as a Queue-backed Worker, not a plain one — a real empirical finding, not a preference. Both of a Worker's execution-extension mechanisms (`ctx.waitUntil`, and staying connected to a caller that is itself `waitUntil`-bound) cap out around 30 seconds, and issue 08's already-measured real numbers (~140 sequential API calls for 45 rows) sit close enough to that ceiling to make it a near-term reliability risk, not a hypothetical one. The `fetch()` handler now only validates + enqueues (fast `202` ack); a `queue()` consumer in the same Worker script does the actual Import Run, with an independent ~15-minute execution budget unrelated to any caller's connection state. `exceljs` confirmed working under the Workers runtime (`nodejs_compat`) against a real sample export. `relay-cloudflare` needed no changes as a result. `ConnecteamClient` duplicated + trimmed into this package too, same isolation reasoning as issue 14.
